# Interchange schemas and version changes

These JSON Schemas use Draft 2020-12. They describe well-formed interchange data:

| Schema | Input |
| --- | --- |
| [Format 2 front matter](format-2-front-matter.schema.json) | The YAML between the opening `---` lines, parsed into JSON-compatible values |
| [Export settings, version 1](settings-file-1.schema.json) | `settings.json` in an export zip |
| [Settings carrier, version 1](settings-carrier-1.schema.json) | The decoded `thundernotes-settings.json` attachment of one account's carrier; also each export `labels` / `labelsByAccount` value |

Load all three schemas into a validator to resolve relative references locally. Their `$id` URLs
identify the schemas at their eventual public-release location; validation needs no network. The
add-on does not bundle a validator. Tests use pinned Ajv in strict mode to compile the schemas,
validate the [format reference files](../../packages/core/test/format-fixtures/), both settings
[examples](examples/), and output generated by `toMarkdown`, `buildSettingsFile` and
`buildSettingsCarrier`.

## Validation and reader behaviour

The front-matter schema requires the documented minimum: `thundernotes: 2`, a non-empty
`message_id`, `body_boundary`, and each annotation's `id` and `quote`. Writers also emit the set's
`created`, `updated`, `rev` and each annotation's timestamps. Omitted timestamps use the reader's
fallbacks (`created`, or the read time when set `created` is missing); omitted `rev` becomes 0.
Settings schemas describe complete writer output; settings readers can salvage incomplete input.

Known fields have their documented types. The readers accept some values outside these schemas:
for example, the front-matter reader coerces some scalars to strings, and settings readers drop
malformed entries. Schema failure therefore does not imply that the add-on refuses the file.
Timestamp patterns check UTC string shape, not calendar validity. Parse YAML timestamps as
strings (the default YAML 1.2 core schema), or normalize date objects to ISO strings first.

Unknown properties are allowed. Readers ignore them and generally drop them on rewrite; they
are not a safe place to keep data that another client must preserve. Annotation colours are
strings because the format reader preserves unknown names (display falls back to yellow);
settings colours use the eight-name palette or `null`, matching the settings reader.
`taskView` is opaque: it backs up the task page's own preferences without promising a stable
cross-client structure. Account keys in `labelsByAccount` are account addresses, not Thunderbird
IDs; account scope for a settings carrier comes from the IMAP account containing it.

JSON Schema checks structure, not all protocol rules. The format reader must also check unique
annotation IDs, valid body frames, matching section IDs and the final separator. Writers must
choose an unused boundary line; position ranges must have end at or after start. Base hashes are
ordered newest first, and `text_base` / `email_note_base` must equal the first entry of the
corresponding list when both exist. The merge semantics are specified in [SYNC.md](../SYNC.md).

## Version-change rules

There are independent version spaces: Markdown front matter (`thundernotes: 2`), the MIME carrier
envelope (`X-Annot-Version: 1`), export settings (`version: 1`), and settings-carrier JSON
(`version: 1`). Changing one does not by itself change the others or the add-on's version.

- An optional field may be added within a version only when ignoring or dropping it is safe.
  Keep existing fields' meaning and defaults. Update schemas, documentation and generated-file
  tests together. The format-2 base lists are an example: `text_base` remains the first hash for
  older readers that do not understand `text_bases`. Another is `image` (a note on a picture,
  D46): with `quote: ""` older readers place the note nowhere and keep its text; one that
  rewrites the carrier drops the field, so the note stays but no longer finds its picture.
- A new required field, incompatible body framing or changed meaning requires a new version
  and a new versioned schema. Keep the older schema and reference files as the old contract.
  A format-2 reader already refuses newer Markdown versions, and the export-settings reader
  refuses settings versions other than 1. Unreadable note carriers remain on the server (D35).
- The current settings-carrier reader sanitizes known entries without checking JSON `version`.
  A future incompatible settings payload must first arrange safe refusal/quarantine by older
  clients, or use a distinct carrier identity they cannot mistake for version 1. Merely changing
  its JSON version is insufficient. This is a requirement for that future change, not behaviour
  the current reader provides.

Format 1 → 2 was a development-only conversion outside the add-on, using the existing
`scripts/migrate-format2/` tools. The add-on rejects format 1; its local database model did not
change. Those tools use a frozen old reader and compare the converted notes after reading them
back. These rules do not change or extend those tools.

Before introducing a future format 3, its change must state which older versions it reads and
how unsupported versions are reported. If existing data must be carried forward, define the
conversion separately: preserve stable IDs, note text, selectors, timestamps, deletion records,
folding, account routing and merge metadata, and prove preservation with old/new reference
files and round-trip tests. Keep originals recoverable and validate a replacement before removing
the old copy. Any intentional information loss needs an explicit design decision. Migration
implementation and migration corner cases remain outside the present development task.
